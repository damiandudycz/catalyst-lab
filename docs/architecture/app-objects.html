How Catalyst Lab is put together

Choose an activity to see which persistent objects and execution components participate, what each one does, and how they depend on one another. These are the app’s domain concepts, not a required setup sequence.

Build a stage

Execution endpoint

Runner

A runner executes primary tools and provides the environment in which a toolset is loaded. Linux uses the Host runner; macOS uses a VM runner. The Runner interface separates operations from the transport so remote runners can fit later.

VM runners use Lima and an Alpine Linux guest. Toolsets refer to a runner by type and identity.

Dependencies
  • Host: Linux; unshare, newuidmap, newgidmap, and unsquashfs; subordinate UID/GID ranges; available unprivileged user namespaces; bubblewrap 0.11.0 or newer.
  • VM: macOS and Lima; the runner-creation flow downloads Alpine Linux. CPU, memory, and workspace capacity are configured when the runner is created.
runner.py
Reusable execution environment

Toolset

A Gentoo stage3 environment with Catalyst and selected primary tools. It is cached in the Library and loaded for builds, snapshot operations, and package work.

A toolset selects its runner and exposes commands through that runner’s executor.

Dependencies
  • A compatible runner and a Gentoo stage3 archive.
  • Catalyst for stage builds; optional applications such as QEMU add their own Portage dependencies.
  • Network access for uncached downloads and package installation.
toolset.py
User configuration

Project

A project is a Git directory containing stage definitions and project-level choices such as architecture, snapshot, Releng template, overlays, and package cache. It does not own a toolset; actions select one when needed.

Its stages form a dependency graph; a build plan selects stages and resolves parent artifacts.

Dependencies
  • Git-backed project directory and at least one configured stage.
  • For builds: a compatible toolset selected in the wizard, snapshot, architecture, and Releng inputs. Catalyst is required; QEMU is also required for emulated architectures.
  • Optional overlays and binary package folders must match the project’s compiler and architecture constraints.
project_directory.py
Build input

Stage

A stage describes a Gentoo image to produce: stage type, architecture, packages, USE configuration, kernel settings, and related options. Catalyst consumes the generated specification.

Dependencies
  • Project architecture and generated Catalyst arguments.
  • Parent stage artifact when the stage is not a seed.
  • Snapshot, Releng template/profile, and referenced overlays or package configuration.
project_stage.py
Reproducible repository state

Snapshot

A snapshot is a captured Gentoo repository tree at a specific commit. Builds and package operations use it so repository changes do not silently alter an existing run.

Projects can select a pinned snapshot or request the latest one when building.

Dependencies
  • Generation: a toolset with Catalyst and access to the Gentoo repository.
  • Use: a snapshot file in Library storage and a build or package operation that selects it.
  • Imported snapshots can be used without a runner.
snapshot.py
Stage configuration source

Releng

Gentoo Release Engineering templates supply profile and configuration inputs used to generate the Catalyst specification and root overlay for a stage.

Dependencies
  • A cloned or local Gentoo Releng repository.
  • The selected template/profile must support the stage architecture and init system.
  • Referenced overlays and template files must remain accessible to the runner.
releng_directory.py
Binary package cache

Packages

Project-selected binary package storage lets compatible builds reuse compiled packages. Architecture and compiler flags constrain which projects can safely share it.

Dependencies
  • A Portage package cache directory in Library.
  • Compatible architecture, compiler flags, and package configuration for sharing.
  • Selected build stages must enable and use binary packages.
packages_directory.py
Persistent output

Build record

Each stage build stores status, timestamps, output, failure diagnostics, reproducibility metadata, and any produced artifact under the project’s Builds directory.

Dependencies
  • Created by a project build process for a selected stage.
  • References the project, toolset, snapshot, source state, and resulting artifact or failure log.
project_build_record.py
Creation operation

Toolset installation

Downloads or reuses a Gentoo stage archive, extracts it in runner storage, installs selected tools, verifies the environment, and compresses the reusable result into the Library.

Dependencies
  • Selected runner and stage3 archive (downloaded or cached).
  • Internet access or usable Portage distfiles and binary package caches.
  • Selected primary applications and their Portage dependencies.
toolset_installation.py
Guest test environment

VM test image

A VM test starts from a prepared image derived from a completed stage. A writable per-run image receives test configuration; cached kernels can be reused when their metadata is compatible.

Dependencies
  • Completed stage artifact and prepared base image.
  • Bootable kernel/initramfs; custom kernel package when the stage lacks a usable kernel.
  • QEMU on Linux or Apple Virtualization on macOS, plus storage for the writable run image.
qemu_run.py
Application data root

Library

The Library stores projects, builds, toolsets, snapshots, Releng data, overlays, packages, runners, and reusable caches. Its library.json records the app version associated with the Library. MIN_LIBRARY_VERSION sets the threshold that decides whether the migration module must run.

Dependencies
  • A configured directory writable by the current user, with space for artifacts and reusable caches.
  • Contains the persistent objects other workflows consume; temporary working files are managed separately.
  • When a stored version is older than the app’s minimum, the migration module updates its data before normal use.
library_version.py · library_migrations.py · app_info.py

The main orchestration is in multi-stage processes. Each process owns ordered operation steps, while domain objects describe reusable inputs and outputs. A runner is the execution boundary; a toolset is the Gentoo environment loaded inside it.
