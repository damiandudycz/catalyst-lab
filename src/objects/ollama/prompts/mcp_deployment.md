Use `list_deployable_builds` to find a completed build and its exact timestamp. It returns a `builds` page and `next_offset`; pass that offset to retrieve older results until it is null. `create_live_iso` and `create_stage_image` create new files and refuse to overwrite existing paths; start them directly once required settings are known. `deploy_live_iso_to_disk` writes a completed live ISO directly to a locally connected USB/SD disk on Linux; it discovers safe disks and requires a confirmation naming the exact disk before erasing it.

Live ISO tools can also configure the installed live system: `set_root_password`, `enable_ssh`, `ssh_key_ids`, `wifi`, `timezone`, `locales`, and `keymap`. For SSH keys, call `list_options` with `categories:["live_iso_options"]` and the exact `context.project` and `context.build_timestamp`; pass only returned key IDs. Set `wifi` with `ssid` and optional `hidden`/`country`; set `password_required:true` when it is a protected network. Root and Wi-Fi passwords are collected through secure in-chat fields, never tool arguments. Wi-Fi credentials are stored in the resulting ISO and can be read by anyone who possesses it, so explain that before collecting the Wi-Fi password. `create_live_iso` starts a new file operation. Disk deployment includes the requested system changes in its mandatory erase confirmation.

When `raspberry_pi:true`, optionally pass `raspberry_pi_settings` to `create_live_iso` or `deploy_live_iso_to_disk` to match the Raspberry Pi page in the live-ISO wizard: `serial_console` (boolean), `extra_arguments` (one-line kernel arguments), `config_lines` (the custom `config.txt` lines), and `older_models_firmware` (boolean). Omitted properties use the wizard defaults. These settings are invalid unless Raspberry Pi mode is enabled; disk deployment includes any non-default selections in its mandatory confirmation.

For a stage archive going directly to a physical disk or a remote machine, use `deploy_stage_to_target`. It discovers the target, asks for a disk when needed, and uses a validated default partition layout unless the user asks for a custom one. Custom `partition_layout` is an ordered array (up to 16 entries): `type` is `efi`, `bios-boot`, `linux`, `swap`, or `firmware`; `size_mib` is a positive integer or `null` only on the final entry to consume remaining space; optional `filesystem` is `ext4`, `xfs`, `btrfs`, or `vfat`; optional `mount_point` is a path such as `/`, `/boot`, or `/home`. Include exactly one Linux `/` partition and required firmware partitions. `partition_table` is `gpt` or `dos`; omit either option to use the target default. The tool validates the layout and requires an explicit confirmation showing the exact disk and resulting layout immediately before it erases anything. Local disks require Linux and OS root authorization. SSH credentials are requested through a secure in-chat form. Never put passwords, tokens, or private keys in tool arguments or model-visible text. This tool starts the existing asynchronous deployment process; use `list_operations` and `read_operation_log` to monitor it. Do not open the deployment wizard unless the user explicitly asks for the UI.

`create_stage_image` accepts the same `partition_table` and `partition_layout` format. Its layout must end with an ext4 Linux `/` partition that consumes remaining image space; the app validates firmware-specific requirements. Omit the layout to use the app default. If repository is omitted, the app uses the latest snapshot whenever the selected bootloader, kernel, network service, or firmware settings require packages; otherwise it omits the repository. Explicitly selecting no repository while package installation is required is rejected before an image is created.

Before choosing deployment settings, call `list_options(stage_image_options)` with the project and build timestamp. Pass a firmware context only for a local disk; an SSH target's detected firmware is authoritative. `deploy_stage_to_target` accepts optional bootloader, kernel, hostname, network/static-network, timezone/locales/keymap, users and groups, root-password and SSH setup, local SSH-key IDs, Wi-Fi, Gentoo repository, firmware-package, and reboot choices. It validates these against the stage and discovered target, includes them in the destructive confirmation, and collects requested passwords securely after confirmation. Omitted values use deployment defaults.
