Use this guide when translating a named Catalyst Lab section or screen into available chat actions. `ask_user` is the shared form tool for collecting genuinely missing choices across sections; discover select options first and use returned defaults or sole choices. These are tool families, not complete schemas: search `list_tools` using the user's goal, then call `read_tool_schema` for the exact tool before using it. Use `list_documentation` and `read_documentation` to find detailed guides. Follow confirmation, option discovery, and async-operation rules in `mcp-actions`.

| UI area | Chat tool families |
| --- | --- |
| App menu | `open_about` opens About and `open_keyboard_shortcuts` opens the shortcuts overlay, only when explicitly requested. Preferences is currently a placeholder in the app and has no chat action. |
| Home / Welcome | `list_sections` reports valid main sections; `open_section` navigates only when explicitly asked. The “Get started” action opens `open_wizard(workflow="initial_setup")` when the user explicitly asks for onboarding. Its pages advance through Library location, Git identity, Environments, Releng, and Snapshots as applicable. Home shortcuts navigate to Projects, Builds, and Deploy; perform requested work with the corresponding direct tools. |
| Projects | `open_project` and `open_object` navigate to a project or object details page only when explicitly requested; they do not perform actions. `list_objects` includes project configuration (architecture, Releng directory, snapshot, packages directory, and effective Catalyst toolset with its selection source); `update_project` manages those settings and project-specific toolset selection. Before changing the Catalyst toolset, call `list_options(categories=["project_toolsets"], context={"project":"EXACT_PROJECT_ID"})` and use a returned ID or `default` to restore the app default. `list_options`, `create_project`, `rename_project`, `check_project_source_updates`, `update_project_template`, `update_project_repository`, and `delete_project` cover project actions and source updates. The project Information page’s Save/Discard Changes actions use `get_git_status`, `list_git_changes`, `commit_git_changes`, and `discard_git_changes`; inspect changed paths first, ask for a commit message, and let the discard tool present its confirmation. Stage configuration uses `create_stage`, `update_stage`, `set_stage_parent`, `delete_stage`, `get_stage_settings`, `set_stage_setting`, `reset_stage_setting`, `remove_unsupported_stage_setting` (asks before deleting a saved unsupported value), `list_stage_kernels`, `update_stage_kernel`, `delete_stage_kernel`, `read_stage_script`, and `write_stage_script` (replacing an existing script asks for confirmation). Stage package selection combines `get_stage_settings`, `list_repository_packages` for the project's snapshot/enabled overlays, and `set_stage_setting`; load `mcp-project-stages` for inheritance and version-atom handling. `open_local_folder(target="stage_overlay")` opens the exact stage-managed overlay folder shown in Stage settings when explicitly requested. |
| Builds | `preview_build_plan` shows the Build wizard's parent-stage rebuild/reuse plan and, with a selected toolset, missing required settings; it never starts a build. `start_build` executes the plan. If the user explicitly wants the visual generated-file preview and its Browse controls, open `open_wizard(workflow="project_build", project)`; do not open the wizard just to perform a build. `list_builds` matches the history status filter (`all`, `completed`, `failed_canceled`) and pages with `offset`/`next_offset`; `get_build_run` reads a grouped run's saved steps and output; `list_build_files` browses paths in one stored build, and `read_build_file` reads a selected file; `open_local_folder(target="build", project, stage, timestamp)` opens that exact saved build folder when explicitly requested. `list_operations` returns active and pending-result operations, running VM, and queued-build IDs; `open_operation` reopens a listed live view only when explicitly requested. Other tools: `delete_build_record`, `delete_build_run`, `read_operation_log`, `stop_build`, `stop_operation`, `resume_build_queue`, `start_vm`, `read_vm_output`, `send_vm_console_input`, `control_vm`. `send_vm_console_input` sends exact user-requested text or supported keys to a running VM's serial console; delivery is not confirmed. For visual VM launch configuration, `open_wizard(workflow="vm_launch", project, timestamp)` opens the existing wizard for an exact completed build; ordinary launches use `start_vm`. |
| Packages | The Binary packages section manages shared compiled-package caches: `list_objects(type="packages")` reports architecture, CPU flags, linked projects, and compatibility issues; `create_packages_directory` takes either the exact `project` ID (the app derives compatibility and can choose a unique name) or both a unique `name` and exact `architecture` for a standalone folder (use `list_options(architectures)` first; CPU flags are optional and default to that architecture); `delete_packages_cache` and `package_cache_stats` (total and per-release-type on-disk bytes, project links, and Portage index counts) manage or inspect a cache; `open_local_folder(target="packages")` opens one when requested. `list_repository_packages` instead browses source ebuilds in Portage snapshots and overlays; it does not inspect binary caches. |
| Environments | Runner tools cover `get_runner_status`, `create_vm_runner`, `set_runner_state`, `update_runner`, and `delete_runner`; `get_runner_status(include_usage:true)` includes live CPU, memory, swap, disk, and workspace usage shown on a running VM runner's details page. `create_vm_runner` supports optional resource overrides within its schema bounds (CPU count also cannot exceed the host count); omitted values match the UI defaults: a unique “Alpine VM” name, up to 8 CPUs at half the host count, 8 GiB memory, 64 GiB workspace, 16 GiB swap, and set as default. `update_runner` uses the same bounds and only changes resources while the VM is stopped. `delete_runner` removes the VM disk and runner-local extracted caches; shared Library files remain on the host and the tool requires confirmation. Change the default with `update_settings` using `setting:"default_runner_id"` and a value from `list_options(runners)` (`default` restores automatic selection). Toolset tools cover `get_toolset_status`, `create_toolset`, `set_toolset_mount`, `update_toolset`, `configure_toolset`, `rename_toolset`, and `delete_toolset`. `get_toolset_status` mirrors the details page's source, dates, size, applications, patches, and active mount bindings. New toolsets use the UI defaults for the recommended stage, name, selected applications, binary packages, and default status. Pass `set_as_default:false` when the user wants to keep the current default. Discover object IDs with `list_objects`. |
| Releng and Overlays | Git-directory tools cover `get_git_status`, `list_git_changes`, `update_git_directory`, `commit_git_changes`, `discard_git_changes`, `create_git_directory`, `rename_git_directory`, and `delete_git_directory`. `get_git_status` is cached; `list_git_changes` reads paths and Git state without file contents or a fetch. Updates fetch/rebase asynchronously. Ask for the commit message before `commit_git_changes`; `discard_git_changes` permanently removes tracked, untracked, and ignored changes after confirmation. Deletion confirms and reports project references. Overlay package browsing uses `list_repository_packages`; discover and read files with `list_object_files` and `read_object_file`. `write_object_file` creates a new file when requested, but replacing an existing file requires confirmation. For creation, call `list_options(git_directory_sources, context={type:...})`: Releng is Git-only, while overlays also allow copying a local directory by absolute path or creating an empty overlay. Load `mcp-git-directories` for workflow details. |
| Snapshots | `create_snapshot`, `import_snapshot`, `delete_snapshot`, `get_snapshot_usage`, `list_options`, and `list_objects`; browse ebuilds with `list_repository_packages`. Before generation, use exact `toolsets` and `runners` options; `default` selects the app default. `import_snapshot` needs an exact absolute path; if the user explicitly wants to choose a file with the native picker, open `open_wizard(workflow="snapshot_create")`. Load `mcp-snapshots` for import, deletion, progress, and automatic-cleanup behavior. |
| Deploy | `list_deployable_builds`, `create_live_iso`, `create_stage_image`, `deploy_live_iso_to_disk`, and `deploy_stage_to_target`. Live ISO tools can configure root password, SSH, listed local SSH keys, Wi-Fi, localization, and Raspberry Pi boot settings (`serial_console`, `extra_arguments`, `config_lines`, `older_models_firmware`); discover SSH IDs with `list_options(live_iso_options)`. Wi-Fi credentials are stored in the generated ISO. Disk writes are destructive and require the tool's confirmation; platform and target limitations are in each schema. |
| Bugs | `list_bugs`, `set_bug_status`, `remove_bug`, `list_bug_notes`, `add_bug_note`, `edit_bug_note`, `delete_bug_note`. Search failures with its case-insensitive `query`, exact `project`, or `status` filters; page through results with `offset` and `limit`. Set `group_by` to `issue`, `package`, `project`, `stage`, or `date` to match the screen grouping; omit it for the flat list. Use `failure_id` values (also returned as `id` for compatibility) or grouped issue keys returned by `list_bugs`. `list_bug_notes(failure_id=...)` reads one issue; pass exact `project` and `package` from `list_bugs` to show the package-level notes overview, grouped by issue and paged with `offset`/`limit`. For a listed failure, use `read_build_file` with `project` = returned `project_id`, `timestamp` = `build_timestamp`, and `path` = `log_file` when `log_available` is true. To browse the Bugs screen’s collected failure files, call `list_build_files` with that project and timestamp, then read a selected path with `read_build_file`. `open_bugzilla` only opens a listed Gentoo failure's page. |
| Library | `list_library_storage(section="overview")` reports total usage and category sizes; `list_objects(type="runner")` covers the Overview runner rows. Inspect the UI tabs with `list_library_storage` sections `cache`, `packages`, `snapshots`, `projects`, and `builds`, paging with `offset`. `temporary` is an additional inspection/cleanup section, not a separate UI tab; `delete_library_storage_item` accepts exact Cache or Temporary entries, and Temporary cleanup is blocked while operations, VMs, or runners are active. Use `delete_packages_cache`, `delete_snapshot`, `delete_project`, `delete_build_record`, or `delete_build_run` for their matching registered objects; each applies its own reference and active-use safeguards. The Snapshots page's automatic-cleanup switch maps to `update_settings(setting="auto_clean_snapshots")` and may ask before removing unused snapshots. `open_local_folder(target="library")` and `change_library_location` cover the location controls; opening requires an explicit request, while changing location confirms the destination and operation and restarts the app. |
| Settings | `get_settings`, `update_settings`, `list_options`, `list_ollama_models`, and `pull_ollama_model`. Use `list_options(library_toolsets)` for the app-wide default toolset, since Settings allows any installed toolset; `toolsets` is a Catalyst-specific list for other workflows. `get_root_access_status` reads the Root Access popover and returns exact call IDs; `set_root_access` enables/disables it only on explicit request, uses the normal OS authorization prompt, and refuses to interrupt privileged actions. `cancel_root_action` requests cancellation by an exact cancellable call ID and may leave partial changes. `open_root_action_output` opens the live output view without passing output to the model. `keep_root_unlocked` is its preference in `get_settings`/`update_settings`. Pull a model only when explicitly requested. |
| AI Assistance | The UI’s “Check connection” action maps to `list_ollama_models`, which contacts the configured server and returns connection errors or installed models. If the user provides a different endpoint, save it with `update_settings(setting="ollama_url", value="USER_PROVIDED_URL")`, then call `list_ollama_models` to verify. `update_settings(setting="ollama_model")` selects an exact installed model for future chats; `pull_ollama_model` downloads only on explicit request. `open_ollama_model_catalog` opens the fixed Ollama catalog linked by “Browse all models” only when explicitly requested. |

Navigation tools are `list_sections`, `open_section`, `open_project`, and `open_object`; use them only when the user explicitly asks to see a section or detail page. `open_local_folder` opens only an app-managed folder and also requires an explicit request. `open_wizard` supports app workflows, including first-run onboarding as `initial_setup` and project build setup as `project_build` with its exact project ID, and VM launch setup as `vm_launch` with the exact project ID and completed-build timestamp; use a wizard only when the user explicitly asks to open it. Otherwise use the direct chat workflow where one exists. If a listed operation is asynchronous, report it as started and use `list_operations` for its state rather than claiming completion.
