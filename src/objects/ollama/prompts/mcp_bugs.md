Load for searching, reviewing, annotating, resolving, or removing entries in Bugs.

Use `list_bugs` for exact `failure_id` values (also returned as `id` for compatibility) and repository names. It supports case-insensitive `query` across package, repository, phase, reason, project, and stage; exact `project`; and one resolution `status`. Page with `offset` and `limit`. Set `group_by` to `issue`, `package`, `project`, `stage`, or `date` to receive Bugs-screen-style groups while retaining exact failure IDs and issue keys; omit it for the original flat-list response. Grouped pages are bounded by failure count, so one group can continue on a later page. Use `failure_id` for an individual entry. For the UI's grouped actions, pass the exact `issue_key` array from `list_bugs` to set status or remove every occurrence in that group; pass exactly one selector to either action. `list_bug_notes` also requires exactly one lookup mode: `failure_id` alone, or both exact `project` and `package` values from `list_bugs`.

`list_bug_notes(failure_id=...)` reads notes on one issue. For the package-level notes overview, pass exact `project` and `package` from `list_bugs`; use returned failure IDs for note edits. Removing an entry or note requires confirmation and keeps build logs. Bugzilla status is not changed by Catalyst Lab; `open_bugzilla` only opens a listed Gentoo failure's page when explicitly requested.

To inspect a failure log, call `read_build_file` with the `project_id`, `build_timestamp`, and `log_file` from the failure result when `log_available` is true. To browse other collected failure files, use `list_build_files` for that project and timestamp, then `read_build_file` for a selected path. For saved build state use `list_builds` then `get_build_run`; for active builds use `list_operations` and `read_operation_log`.
